## 1. 范围、证据与结论

### 比较基线

- **我们**：[yukariyukaro/bilibili-cli](https://github.com/yukariyukaro/bilibili-cli)。本地 HEAD 为 `21ac3b1235081b207729b3a60d40b816f5676dc4`，包清单版本为 2.0.0；**本文以含未提交修改及新增文件的当前工作区为准**，尤其是 bridge / Web 控制台，不代表这些能力已经发布到 GitHub 或 npm。
- **目标**：[kukemc/bili-cli](https://github.com/kukemc/bili-cli)，固定比较提交 [`a8fc4c8c97ddc8b31e6ecdab313076ddbb1107bf`](https://github.com/kukemc/bili-cli/tree/a8fc4c8c97ddc8b31e6ecdab313076ddbb1107bf)。其 README 自述为“80+ 命令、18 个 Agent、17 个 MCP 工具”；不沿用旧分析的“93 个”作为当前精确总数。
- 我方当前注册表为 **27 个公开命令定义（含 4 个 bridge 命令）**，其中也包含配置、诊断、schema 与技能发现，不能称为“27 个业务能力”。目标的命令拆分方式不同，数量不能直接衡量完成度。
- 证据标记：**本地源码**＝可定位的注册/执行路径；**目标静态**＝固定提交的文档或源码；**历史记录**＝仓库已有验收台账；**待验证**＝本轮没有运行证据。静态实现不等于真实接口成功。

### 当前结论

1. **真实的覆盖差距存在**：目标已提供更广的内容发现、视频理解、互动、创作和运营入口；我方当前公开 CLI 尚无这些完整闭环。用户正在补能力，后续按源码、安装产物和发布状态逐项更新，不能把“在做”写成“已交付”。
2. **先澄清 R01–R03 的安全与执行边界，再优先补开源协作入口与用户文档**：Issue 表单、贡献说明、安全报告入口、FAQ、完整任务示例和 bridge 运维指南，比为了命令数平齐而同时开投稿、ASR、MCP 更合适。
3. **skills.sh、无 MCP、bridge 不直接算落后**：它们是分发或架构选择；要记录相应的适用范围、成本和证据缺口，而不是要求照搬对方。
4. **我方优势也有边界**：稳定信封、严格参数校验、JSONL、写开关和正文哈希审计值得保留；不能据此声称所有路径都有人工审批、所有状态都不存正文、或已经完成无人值守真实往返验收。

“全部短板”在本文中指**本次已核对范围内的完整差距登记**，不是穷尽两个仓库所有隐性缺陷；没有证据的项目标为待验证，不用推测补齐。

## 2. 对旧分析的必要修正

| 旧判断 | 修正后的判断 | 应如何处理 |
| --- | --- | --- |
| skills.sh 安装不如自动装进 18 个 Agent | 我们复用通用 Skill 分发生态，不需要自己维护 18 套安装逻辑；目标的优势是内置检测与引导体验，不是支持面必然更大 | 保留 skills.sh，补兼容/安装方式/更新边界说明 |
| skills.sh 理论上所有 Agent 都能用，而且没有重复 | 对支持 Skill 且能执行命令的 Agent 具有较好可移植性；实际仍取决于宿主发现路径、安装器支持与权限。canonical + 链接可减少副本，copy 模式、不同 scope 和历史安装仍可能重复 | 写“共享单一来源、减少重复”，不写“所有 Agent 保证兼容、零重复” |
| 没 MCP 就必须补 MCP | CLI + Skill 已适配可执行命令的 Agent；不要求为普通查询启动 MCP。只支持 MCP、无法执行命令的客户端仍是实际接入缺口 | 按需求评估可选适配层，不列为近期必做 |
| 不用 MCP 一定更快、更省资源 | 普通 CLI 工作流不要求额外启动工具服务；总性能还受 CLI 冷启动、进程复用、JSONL、网络和宿主影响。MCP 也不一定是常驻网络服务 | 没有实测，不下 CPU、内存、延迟优劣结论 |
| bridge 可以替代 MCP | bridge 处理长期事件、外部 Agent 连接、调度与控制；MCP 处理宿主发现和调用工具，两者职责不同 | 说明组合关系，不写协议等价替代 |
| bridge 是偏题，应该冻结或移除 | 对“持续任务 + 本机控制台”定位，bridge 是合理的差异化基础；但依赖、审批、任务回执和恢复都需要维护 | 保留可选边界，先把现有链路和文档做实 |
| 同一上游，所以两边 API 一定同水平 | 共同来源不保证版本、移植覆盖、解析精度、风控处理和真实接口行为一致 | 分别验证，不用血缘替代测试 |
| 目标固定上游，所以无法修复 | 固定版本确有升级维护成本，但仍可 fork、补丁或替换；我方自维护移植层也承担接口跟进成本 | 不用“结构性天花板”推导必然失败 |
| 两边都有登出 | 我方当前注册表没有 `auth logout`；目标命令表包含它 | 单列账户生命周期缺口，禁止把手工删凭证当公开登出流程 |
| 我方所有写入都有逐次人工确认 | CLI 强制检查开关和确认参数，但不能验证参数背后是否真有人同意；bridge 的 owner 策略会自动放行 | 见第 5 节安全闭环缺口，不能只靠宣传用语掩盖 |
| 我方不保存正文 | `audit.jsonl` 的正文只记哈希；bridge pending、草稿及外部 Agent 会话可能有正文 | 文档说明全链路数据落点与保留边界 |
| Star、下载量、测试文件数能证明可靠性 | Star 是关注度；下载含重复/自动化；测试文件数量不代表场景覆盖；CHANGELOG 修复频繁也不能单独证明不可靠 | 不将这些数字作为质量排名或排期依据 |

Skill 分发机制参考 [skills CLI 文档](https://www.skills.sh/docs/cli)；共享与复制模式参考 [skills 安装方式](https://github.com/vercel-labs/skills/blob/main/docs/commands.md#installation-methods)，宿主差异参考 [Agent 兼容说明](https://github.com/vercel-labs/skills/blob/main/docs/agents.md#compatibility)。这些外部说明为本次读取的动态文档，不与目标固定提交混算。我方现有升级边界见 [Skill 安装与升级](../../skills/bilibili-cli/references/skill-upgrade.md)。

目标安装器主要写共享目录，并向部分已存在的宿主目录复制独立副本（见 [skills.py][target-skills]）；所以我方复用链接式分发确有减少重复维护的价值，但目标也不是“18 套独立运行时”。目标 MCP 使用 stdio 并通过子进程调用 CLI（见 [mcp_server.py][target-mcp]），不能把它概括成必然多一个常驻 HTTP 服务。

## 4. 分发、Agent 体验与架构取舍

| ID | 类型 | 已有基础 | 尚需解决 / 验收方式 |
| --- | --- | --- | --- |
| A01 | 体验缺口，不是覆盖劣势 | skills.sh 统一分发纯文档，CLI 单独安装；无需在每个 Agent 下复制运行时 | 列出已验宿主/平台、scope、canonical/link/copy 与失败处理；不为每个 Agent 再写安装器 |
| A02 | 版本诊断缺口 | doctor / skills list 有 CLI 与随包文档版本 | 不会自动核验宿主实际加载的另一份 Skill。说明如何人工核对；一键 status/link 是后续方案，不能写成现有命令 |
| A03 | 可选生态缺口 | 能执行命令的 Agent 使用 CLI + Skill | MCP-only 客户端无法直接接入。若有真实需求再评估薄 MCP adapter，保持写保护一致；不启动默认服务、不把运行时复制进 Skill |
| A04 | Agent 易用性 | schema、固定信封/退出码、JSONL 行级隔离 | 相对目标 `hint`、`reply_with`、`list_with`，我方下一步引导与精简卡片较少。先补错误码行动表和示例，未来增字段需兼容评审；远端诱导不能成为可执行指令 |
| A05 | 工作流与上下文成本 | 原子命令可组合，JSONL 可复用进程 | 缺稳定的“搜索→字幕→评论→引用”任务配方、长文本裁剪与部分失败范式；性能需量测，不能只数进程或协议层 |
| A06 | 文档自动化 | help/schema/JSONL 共用契约，已有快照与文档门禁 | 用户命令手册仍需检查同步；可由契约生成命令表，同时人工维护限制/副作用/案例，不照搬目标“自动生成所以永不过期”的承诺 |
| A07 | 差异化方向 | bridge + 本机控制台 + 调度代码已有实现 | 连接与任务编排可持续扩展，但不能替代缺失的 B 站原子能力；状态回执、恢复、权限和长期成本须有验收 |
| A08 | 外部依赖/运维成本 | cc-connect 引擎不随包打包，普通 CLI 不需要启动它 | 需要一份支持版本/连接协议/启动拓扑/健康检查/停止恢复指南；说明哪个进程负责什么，缺依赖时怎样退出 |

### 三层职责必须分清

```text
Skill：告诉 Agent 怎么使用、如何核对来源和取得授权
CLI：执行有限命令、校验参数与写开关、输出契约和审计
Bridge / Web：可选的长期监听、任务调度、配置与状态控制
```

MCP 是另一种工具接入协议，不是上述第三层的同义词。普通查询不应为 bridge/MCP 付出必需服务成本；用户选择持续自动化时，则要承认常驻连接、轮询与控制台的成本。**“上限更高”目前是架构潜力，不是已证明比目标更强的交付结论。**

## 5. 安全、可靠性与证据缺口

这些项目不一定意味着目标更强，有的是我方现有承诺尚未闭环。仍应列入同一份差距表，避免只对外找问题。

| ID | 优先级 | 当前证据与缺口 | 完成标准 |
| --- | --- | --- | --- |

| R02 | P0 | 审计正文只存 SHA-256，但 pending 和草稿含正文，数据还会送到外部 Agent；哈希也不等于匿名化 | 发布数据落点/用途/保留/清理边界，覆盖日志、状态、草稿、会话与报告；禁止要求用户上传整个状态目录 |

## 6. 近期重点：Issue 模板与文档产品化

### 6.1 开源协作入口

本仓库当前 `.github/` 主要是 workflows，未见以下协作文件；目标固定提交已提供 [Issue 表单][target-issues]、[PR 模板][target-pr]、[贡献说明][target-contributing]、[安全政策][target-security] 和[免责声明][target-disclaimer]。这是低成本、可直接改善协作质量的明确差距。

下表是**建议交付，不是本次已经创建**。路径供后续排期，不在本文复制完整模板。

| ID | 优先级 | 建议交付 | 必要内容 | 验收 |

**建议 Bug 表单最少收集的信息**：

- 版本：CLI、当前实际加载的 Skill、API 包、Node 与 OS；不要仅看随包 Skill。
- 安装：npm 发布包/源码验收、全局或项目 scope、链接或复制；不收真实用户路径，必要时脱敏。
- 复现：最小命令/参数形状、退出码、结构化错误；BV/UID 是否需要公开由报告者决定。
- bridge/Web：哪一个入口、哪个阶段、是否仅离线复现、状态路径是否一致；只报告 token 是否配置，不报告值。
- 写入问题：是否已人工核对平台结果，明确停在失败/未知状态，不要求为复现再次发送。
