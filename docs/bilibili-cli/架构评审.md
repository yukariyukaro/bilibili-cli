# bilibili-cli 架构评审（残余项）

评审时间：2026-10-22。状态：**本轮已修复项已移出正文，只保留残余问题与验证边界**；修复清单见 [CHANGELOG](../../packages/bilibili-cli/CHANGELOG.md) 的 2.0.0。

评审范围：`packages/bilibili-cli/`、`skills/bilibili-cli/`、根 README、产品 README、`docs/bilibili-cli/`、发布工作流与 Docker 验收脚本。

## 1. 结论

分发层的三类核心问题已经收敛：

1. **入口策略有单一事实源**：全局安装优先、不做 CLI 的 npx 兜底；安装命令只保留在 CLI 契约一处，并用 `npm test` 的文档门禁防止再次分叉。
2. **Skill 与 CLI 有版本绑定**：SKILL.md 的 `metadata.version`/`metadata.requiresCli`，`doctor.skill` 与 `skills list/read` 均可报告 CLI 版本、文档版本与是否匹配。
3. **职责边界回收**：`skills cleanup` 已移出公开 CLI，改由仓库维护脚本执行；bridge 不再依赖 PATH 上的同名命令。

运行时代码的分层（契约单一源、写保护集中、发布闭包、真实安装路径测试）保持不变。

## 2. 残余问题

### 2.1 P2：三个测试驱动仍偏长

- `test/bridge/protocol-driver.mjs` 约 1400 行。
- `test/bridge/lifecycle.mjs` 约 1150 行。
- `test/bridge/docker/run.mjs` 约 750 行。

单行 re-export 已合并，MANUAL 用例已改为 TODO，`min_seqno` 已改为带编号的已知问题诊断；但按场景拆分仍会牵动共享 harness 和进程夹具，风险高于当前收益，留作单独任务。拆分前不要为了行数移动测试入口或放宽断言。

### 2.2 P2：Skill 安装器是否识别 `metadata.requires.bins` 未验证

该字段只是“声明 Skill 需要 `bilibili`”，不能证明 `npx skills add` 或其目标 Agent 会替用户安装 CLI。当前实际保障仍是文档要求的：先检测 `bilibili --version`，缺失时说明理由并取得用户同意后全局安装。若要把它变成可依赖的机制，需要逐个验证目标安装器的行为，而不是继续堆文档。

### 2.3 P2：重构后尚未重跑真实 B 站只读 E2E

默认 `npm test` 是交付链 + 离线 bridge E2E：构建、pack、临时全局安装、仓库外 PATH、本地控制面 WebSocket、隔离状态下的 AUTH 拒绝；**默认不访问 B 站网络**。

真实只读需要 `BILIBILI_E2E_READONLY=1` 等显式配置与已登录账号。上一轮（仓库重构前）真实只读结果为 18 pass / 1 fail / 3 skip，红灯是未证实的 `min_seqno` 断言；该断言已改为带编号的已知问题诊断。2.0.0 本机复验：CLI 真实只读 16 组通过；bridge 真实只读 22 tests / 18 pass / 0 fail / 1 skip / 3 todo（账号 A + 互关账号 B），未执行真实写。CI live job 仍因未配置 secret 而 skip，不能当作真实只读通过。

### 2.4 P3：阶段 2.5 的 `skills status` / `skills link` 未实现

2.0.0 已能检测 CLI 与 Skill 文档版本是否同源，但没有只读诊断命令，也没有一键对齐安装形态的能力；发布形态 A/B/C 仍未裁决。见 [路线图](./bridge实施路线图.md) 第七节与 U20–U22。
