评审时间：2026-10-22。状态：**只保留未解决问题**；已落地的入口策略收敛已移出问题清单，当前口径见第 2 节。
评审范围：`packages/bilibili-cli/`、`skills/bilibili-cli/`、根 README、产品 README、`docs/bilibili-cli/`、发布工作流与 Docker 验收脚本。

## 1. 总体结论

**运行时代码的分层仍然合理**（见第 4 节）。剩余问题集中在四类：

1. **Skill 与 CLI 仍无版本绑定**：npm 包内文档与 git Skill 目录是两条交付通道，互不感知。
2. **文档一致性仍无门禁**：入口说法已统一，但安装命令与规则仍有多处副本，下次改动仍可能分叉。
3. **残余耦合与契约偏差**：bridge 依赖 PATH 上的全局 CLI；分发域清理逻辑仍在内容 CLI；`doctor --setup` 与 schema 默认值仍违背“契约即事实”。
4. **结构迁移后验收脚本未同步**（本次新增）：两套 Docker 验收实际已不可用，而 `npm test` 不覆盖它们，CI 仍是绿的。

## 2. 已裁决并落地的入口策略

**决策：全局安装优先，不做 CLI 的 npx 兜底。**

1. 先检查 `bilibili --version`；已安装就直接使用，并运行 `bilibili doctor --json` 核对版本与依赖，不重复安装。
2. 未安装时说明理由、取得用户同意后执行 `npm install -g @yukariyukaro/bilibili-cli@^1`，再用 `--version` 与 `doctor --json` 核验。
3. 用户不同意或环境装不上：如实说明 CLI 依赖未满足并停止调用，不自动切换到 npx，也不拿源码目录脚本冒充已安装 CLI。
4. `npx skills add/update/remove` 仍保留：它管理 Skill 文件，不是 bilibili CLI 的运行方式。

理由：npx 每次冷启动、依赖 registry 可达性，且 `@1` 是浮动范围，难以与文档承诺的行为一致；bridge 又必须以子进程调用 PATH 上的 `bilibili`。

落地状态：SKILL.md、cli-contract.md、bridge.md、skill-upgrade.md、根 README、产品 README 已统一为同一条路径（检测 → 征得同意 → 全局安装 → 核验）。

需要知道的限制：`metadata.requires.bins` 只是声明 Skill 依赖 `bilibili`，不能证明安装器会替用户安装；目标 Agent/Skill 管理器是否识别该字段尚未验证。因此文档中的显式检测与征求同意仍是唯一实际保障。

## 3. 待修问题

### 3.1 P0：Skill 与 CLI 没有版本绑定

证据：

- [application.mts](../../packages/bilibili-cli/src/lib/application.mts#L59)：`skills list` 返回 `{name, version: VERSION}`，这是 **CLI 版本**；`skills read`（第 60 行）读取 npm 包根目录的 `SKILL.md`。
- [build.mjs](../../packages/bilibili-cli/scripts/build.mjs#L17-L20)：构建时把 `skills/bilibili-cli/` 的文档复制进发布目录；而 `npx skills add` 是从 git 的 `skills/` 复制。同一份文档因此有两条交付通道，两边都没有版本号。
- [SKILL.md](../../skills/bilibili-cli/SKILL.md) 的 frontmatter 只有 `name`、`description`、`metadata.requires.bins`，没有文档版本或所需 CLI 版本；`doctor` 也没有安装一致性段。

影响：无法判断 Agent 手里的文档对应哪个 CLI；升级一侧不会提醒另一侧；旧文档会持续教 Agent 走旧入口。

修复方向：在 frontmatter 增加文档版本与所需 CLI 版本；`skills list` 分别报告 CLI 版本、文档版本与来源路径，不再复用同一个 `version` 字段；`doctor` 增加一致性检测。发布形态（预编译随 Skill 分发 / 首次自举 / 显式对齐）仍需单独裁决，见路线图阶段 2.5。

### 3.2 P1：文档一致性没有门禁

- [verify.mjs](../../packages/bilibili-cli/scripts/verify.mjs#L81-L96) 只断言目录形状、文件存在与构建副本逐字节相等，**不校验跨文档的语义一致**。
- 安装命令块目前仍在四处重复：[SKILL.md](../../skills/bilibili-cli/SKILL.md)、[cli-contract.md](../../skills/bilibili-cli/references/cli-contract.md)、[根 README](../../README.md)、[产品 README](../../packages/bilibili-cli/README.md)；[bridge.md](../../skills/bilibili-cli/references/bridge.md) 与 [skill-upgrade.md](../../skills/bilibili-cli/references/skill-upgrade.md) 另有转述。

影响：这次靠人工统一了说法，但没有任何机制阻止下一次只改其中一份。

修复方向：安装规则只保留一个权威段落，其余改为一句结论并链接；加轻量文档断言，优先覆盖三条：用户安装段不得出现 npx 运行 CLI、安装命令块只允许一处、命令表与 `schema --json` 一致（维护者的 `npm exec` 验收命令单独放行）。

### 3.3 P1：bridge 与安装方式硬耦合

[backend.mts](../../packages/bilibili-cli/src/lib/bridge/backend.mts#L69) 固定 `command = 'bilibili'`，从 PATH 启动子进程；Windows 下还要经过 `cmd.exe` 处理 `.cmd` shim（第 99-113 行）。[bridge.md](../../skills/bilibili-cli/references/bridge.md#L7) 与产品 README 因此只能把“全局安装”写成前置条件。

影响：当前全局安装策略下功能可用，但“bridge 是否可用”变成安装方式的副作用；PATH 被遮蔽、换用其他安装形态或未来允许 npx 时，核心功能会直接失效。

修复方向：默认改为 `process.execPath` + 当前模块入口（或构建时注入的入口路径）自举，使 bridge 与安装形态解耦；保留 `command` 可注入，故障测试能力不受影响。附带收益是去掉 Windows `.cmd` shell 分支。

### 3.4 P1：skill-upgrade.md 仍有死链

[skill-upgrade.md](../../skills/bilibili-cli/references/skill-upgrade.md#L28) 第 28 行链接到 `../README.md`。在 npm 包里这个路径恰好存在，但 `skills add` 只复制 `SKILL.md` 与 `references/`（[verify.mjs](../../packages/bilibili-cli/scripts/verify.mjs#L85-L86) 也断言了目录形状），装成 Skill 后该链接必然失效。

修复方向：改为指向仓库或 npm 包页面的绝对 URL；顺带确认其余相对链接都限定在 `references/` 内。

### 3.5 P1：分发域逻辑侵入内容 CLI

[skill-cleanup.mts](../../packages/bilibili-cli/src/lib/skill-cleanup.mts)（466 行）与 [legacy-skills.mts](../../packages/bilibili-cli/src/lib/legacy-skills.mts)（188 行）把本仓库三段 git 历史的逐文件 SHA-256 固化进了 B 站 CLI，并作为 `skills cleanup` 命令发布。

影响：

- 每次修改技能文档都可能让白名单失效，表现为保守拒绝（CONTEXT 已记录 false-negative）；
- CLI 需要知道“自己这个技能的历史长什么样”，而它又不知道当前安装的是哪一版（见 3.1），职责自相矛盾；
- 公开命令里有 3 条与 B 站内容无关。

修复方向：迁移为独立的维护脚本或安装器能力；若短期保留，至少把哈希清单改为构建期生成的清单文件，而不是手写常量，并明确它只服务本仓库维护者。

### 3.6 P1（新增）：结构迁移后 Docker 验收未同步

bridge Docker 套件：

- [run.mjs](../../packages/bilibili-cli/test/bridge/docker/run.mjs#L39-L48) 仍把 `SKILL.md` 与 `references/` 当作 `packages/bilibili-cli/` 下的文件。现在执行 `node test/bridge/docker/run.mjs --check` **exit 1**：`缺少 CLI 发布闭包文件：SKILL.md`。
- [Dockerfile](../../packages/bilibili-cli/test/bridge/docker/Dockerfile#L24) 的 `COPY` 混用新旧路径（第 24、32、33 行），例如 `COPY packages/bilibili-cli/package.json skills/bilibili-cli/package-lock.json ./`；而 `packages/bilibili-cli/` 下已没有 `SKILL.md`、`references/`。
- [container/entry.mjs](../../packages/bilibili-cli/test/bridge/docker/container/entry.mjs#L44-L45) 仍按 `skills/bilibili-cli/test/bridge/` 前缀校验 manifest，迁移后 manifest 路径是 `packages/bilibili-cli/test/bridge/...`，会得到 `checked === 0`。

release Docker 套件：

- [Dockerfile](../../packages/bilibili-cli/test/release/docker/Dockerfile#L20) 仍 `COPY skills/bilibili-cli/test/release/lib`、`COPY skills/bilibili-cli/test ...`，并把 `BILIBILI_E2E_CLI_ROOT` 设为 `/workspace/skills/bilibili-cli`（第 50 行）；[entry.mjs](../../packages/bilibili-cli/test/release/docker/entry.mjs#L23) 的默认值同样是旧路径；[run.mjs](../../packages/bilibili-cli/test/release/run.mjs#L52) 的用法文本也还写着 `skills/bilibili-cli/test/release/run.mjs`。
- `node test/release/run.mjs --check` 当前通过，但它**不校验 COPY 路径是否存在于构建上下文**，所以真正的失败会被推迟到 `docker build`。

影响：`npm test` 不含 Docker，CI 因此仍是绿的；但 `npm run test:bridge:docker` 在静态检查阶段就失败，`npm run test:release:docker` 会在镜像构建阶段失败。两套隔离验收目前都不可用。

修复方向：把“CLI 源码根”与“Skill 文档根”拆成两个变量（`packages/bilibili-cli` 与 `skills/bilibili-cli`），context 顶层相应加入 `packages`；静态检查增加“Dockerfile 的每个 COPY 源都必须在 context 中存在”的断言；同步入口默认值、manifest 前缀与用法文本。

### 3.7 P2：`doctor --setup` 没有行为

[contract.mts](../../packages/bilibili-cli/src/lib/contract.mts#L42) 为 `doctor` 声明了 `setup` 参数（默认 `false`），但 [application.mts](../../packages/bilibili-cli/src/lib/application.mts#L85-L97) 无条件执行 `runtime.setup()`，从未读取该参数。`schema --json` 因此对外承诺了一个没有行为的开关。

修复方向：删除该字段，或让 `setup=false` 时只返回轻量信息。二者择一，保持“契约即事实”。

### 3.8 P2：schema 默认值不等于运行值

`bridge run` 的 `pollMs` 在契约里默认 6000，但 [command.mts](../../packages/bilibili-cli/src/lib/command.mts#L37-L49) 刻意在未显式传参时不下发默认值，以便 `BILIBILI_POLL_MS` 生效；`ownerUids`、`url` 也有同类环境变量回退。

影响：`schema --json` 说默认 6000，实际可能是环境变量值。对把 schema 当机器契约的调用方是误导。

修复方向：在 schema 字段上增加 `defaultSource: 'env' | 'literal'` 一类标注，或把环境变量回退写进字段描述，使契约与行为一致。

### 3.9 P2：测试信号仍被稀释

- [02-roundtrip](../../packages/bilibili-cli/test/bridge/e2e/02-roundtrip.test.mjs#L4-L5)、[03-order](../../packages/bilibili-cli/test/bridge/e2e/03-order.test.mjs#L4-L5)、[04-baseline](../../packages/bilibili-cli/test/bridge/e2e/04-baseline.test.mjs#L4-L5) 是 MANUAL 占位，计入“跳过”而不是“覆盖”。
- 真实只读套件仍保留一条红灯（`min_seqno` 断言），见 [CONTEXT](./CONTEXT.md#L72) 与“已知限制”；永久红灯会让整套测试失去“全绿即健康”的判断力。
- `test/bridge/protocol-driver.mjs`（约 1400 行）、`lifecycle.mjs`（约 1150 行）、`docker/run.mjs`（约 750 行）单文件承载场景过多。
- [ws-server.mjs](../../packages/bilibili-cli/test/bridge/e2e/lib/ws-server.mjs) 与 [conversation.mjs](../../packages/bilibili-cli/test/bridge/e2e/lib/conversation.mjs) 只有一行 re-export，是不产生价值的间接层。

修复方向：把已知失败用例显式标记为 xfail 并挂问题编号，与“通过”分开统计；合并纯 re-export；按场景拆分超长测试文件。是否引入快速单元层需要权衡——AGENTS.md 明确要求以真实交付路径 E2E 为主，不为速度新增脱离交付链的孤立单测。

### 3.10 P2：路线图仍按旧布局描述“当前源码”

[bridge实施路线图.md](./bridge实施路线图.md#L5) 第 5 行仍写“文档集中在 Skill 产品目录”“未移动 Git 根目录”；第 33 行仍称“唯一 CLI 与 bridge 产品源码位于 `skills/bilibili-cli/src/`”；第 376、403 行也把 CHANGELOG 与依据文件写成旧路径。内容作为历史记录可以保留，但“当前位置”的表述已与仓库结构不符，新会话容易照着旧路径找文件。

修复方向：给历史段落加时间标记，把描述“当前源码位置”的句子改为 `packages/bilibili-cli/` 与 `skills/bilibili-cli/` 两个根；CHANGELOG 路径改为 `packages/bilibili-cli/CHANGELOG.md`。

### 3.11 P3：发布目录 `skill/` 与 tarball 不一致

[build.mjs](../../packages/bilibili-cli/scripts/build.mjs#L29-L30) 在发布目录里生成 `skill/`，但 [package.json](../../packages/bilibili-cli/package.json) 的 `files` 白名单不含 `skill`，`npm pack` 会静默丢弃。产品 README 又描述“生成目录中的 `skill/`……”，容易让维护者误以为发布包内也有该目录。

修复方向：明确 `skill/` 的用途（若只服务于非 npm 分发则写清），或从构建产物中移除，避免“看起来会被发布”的错觉。

### 3.12 P3：命名与措辞（剩余两项）

- [package.json](../../packages/bilibili-cli/package.json) 的 `description` 写的是“自包含的 B 站研究、扫码登录与显式确认评论 CLI 技能”，把 CLI 和 Skill 两个交付物混在一个字段里。
- 状态目录与 `BILIBILI_SKILL_HOME` 仍使用 `bilibili-skill`，与“CLI”的产品定位不一致；[cli-contract.md](../../skills/bilibili-cli/references/cli-contract.md) 只写了默认路径，没有说明这是历史兼容。

修复方向：CLI 包描述只描述 CLI；契约中补一句命名沿用原因，或给出重命名与迁移方案。

## 4. 已确认的优点

- **契约单一源**：[contract.mts](../../packages/bilibili-cli/src/lib/contract.mts) 同时驱动帮助、schema、参数校验与 JSONL；[command.mts](../../packages/bilibili-cli/src/lib/command.mts) 只做装配。
- **写保护集中**：[application.mts](../../packages/bilibili-cli/src/lib/application.mts#L127-L144) 统一处理 dry-run、写开关、逐次确认、attempt/accepted 审计与未知状态，没有散落到各命令。
- **发布闭包可验证**：[closure.mjs](../../packages/bilibili-cli/scripts/closure.mjs) 强制依赖白名单、导入不越界、发布文件固定；发布工作流还交叉校验 tag 与 `package.json` 版本。
- **测试走真实交付路径**：[verify.mjs](../../packages/bilibili-cli/scripts/verify.mjs#L62-L68) 在仓库外通过 PATH 调用安装后的 CLI，而不是直接导入源码；npx 路径也有一条独立的本地 tarball 验收用例。

## 5. 建议顺序

1. **恢复验收能力**：先修 3.6 的两套 Docker 路径与静态断言，再谈其他验收结论。
2. **P0 版本绑定**：3.1 加文档版本/所需 CLI 版本，`doctor` 与 `skills list` 能回答“文档与 CLI 是否同源”。
3. **低成本一致性**：3.4 死链、3.10 路线图路径；随后做 3.2 的文档门禁。
4. **P1 解耦**：3.3 bridge 自举入口；3.5 把 `skills cleanup` 迁出内容 CLI。
5. **P2 契约清理**：3.7 `doctor --setup`、3.8 schema 默认值；3.9 测试占位与永久红灯显式化。
6. **P3 清理**：3.11 发布目录 `skill/`；3.12 命名与描述。

第 1 项优先，因为它决定后续所有“已验证”的说法是否可信；第 2、3 项决定文档能否长期只改一处。
